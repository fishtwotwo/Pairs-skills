# 优化与升级

本技能版本写在 VERSION；底层 CLI、微信和辅助源码版本独立记录，不能混为一次升级。

## 版本保留策略

采用“当前版 + 上一份验证可用版”的滚动保留策略，不无限累积每次修改的完整副本。上一稳定版按实际验证结果选择，不能简单认定版本号紧邻的上一版就是稳定版。

- 当前版：保留当前安装文件，以及需要跨设备迁移时的当前迁移包。
- 上一份验证可用版：保留可恢复的技能、对应被修改的运行组件和必要入口，并保留其测试结果，供回滚及新旧对照。不同平台分别记录验证范围；Mac 尚未实机验证不能因 Windows 测试通过就被标为 Mac 稳定版。
- 更早的普通完整备份：新版本按本次变更范围验收通过，且确认上一稳定版可恢复后，列入清理，不再默认永久保留。
- 重大改动前的版本：更换密钥获取、数据库读取、配置结构、平台支持等可能影响恢复的改动，可临时额外保留一份，并记录保留原因及复查条件；风险解除后回到常规保留数量。
- VERSION、CHANGELOG.md、差异及必要测试结论长期保留；文档修订等低风险小改只需保存小型差异或原文件，不重复复制整套二进制。文档变更按文档校验验收，不为“验收”额外读取聊天。
- 迁移包只保留当前版及上一稳定版；同版本的中间产物、重复 ZIP、临时构建包在确认正式包完整后列入清理。迁移包不是账号或聊天数据备份。

升级顺序：升级前保留可回滚状态 → 修改与验证 → 记录实际验收范围 → 确定上一稳定版 → 按保留策略整理旧副本。新版验收失败或回滚依赖不清楚时，先保留现有副本，不抢先轮换或删除。

清理仅限本技能生成、已核对绝对路径及用途的备份、迁移包和临时构建产物；排除微信数据库、账号配置、密钥、聊天导出、用户手工备份和其他项目文件。不按宽泛通配符删除，不递归删除整个工作目录。清理前记录将保留及删除的具体对象；已有明确授权的例行清理无需重复询问，但仍遵守运行环境对删除动作的审批要求。用户只要求修改说明或讨论策略时，不实际删除历史文件。

## 升级步骤

1. 用户提出相关优化/升级后，先读现有文件、版本、来源和已知限制；只做文件级检查。不要为检查技能而读取聊天或自动扫描密钥。
2. 按上述保留策略，在用户控制的本机目录保留本次修改所需的可回滚状态；普通代码/运行组件更新保留完整可恢复副本，文档小改只保留差异或原文件。备份不收集密钥、数据库和正文，保留必要旧入口，不自动向远程仓库备份。
3. 在独立副本做小范围修改，保留来源和许可证。更新 VERSION、CHANGELOG.md、安装指引与已知限制。设置文件保留目标电脑配置，不用模板覆盖现有配置。不要自动运行下载的安装脚本或拉取 latest 替换已工作版本。
4. 先做离线验证：`python -X utf8 -m unittest discover -s scripts -p "test_*.py"`，测试覆盖授权拒绝、保存拒绝、分页重复/失败、重名、时区、同秒排序。技能格式验证可使用 Codex skill-creator 的 quick_validate.py（需要 PyYAML）。不应为测试调用真实联系人或读全库。
5. 只有用户已指定会话、时间和输出范围并授权时，才做小范围在线回归。报告真实结果；没有进行在线读取就写“未进行”，图片失败不得标通过。
6. 离线验证通过后按授权同步到已安装目录；更新前显示或记录差异。若涉及新的数据去向、安全权限、第三方软件、后台任务或账号范围，必须单独确认具体新增动作，不能借升级扩权。
7. 失败时恢复备份的代码/二进制和入口，保留用户数据与密钥，不通过清空配置制造“干净环境”。新版本与旧版配置不兼容时先设计可逆迁移，不直接覆盖。

不要把单次故障变成无限重试流程。图片扫描目前仍未成功，只允许在有新证据/修复变化且用户明确授权时再验证。
